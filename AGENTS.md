# AGENTS.md — pdmux

Guidance for AI coding agents (Claude Code, Codex, Cursor, Copilot, …) working in
this repository. It was generated by [PodoKit](https://github.com/podosoft-dev/podokit).
Follow it so your changes match the project's conventions.

## Project overview

A Bun 1.4 full-stack TypeScript monorepo (Bun workspaces):

- `apps/api` — **Elysia on Bun** backend (`pdmux-api`), TypeORM + PostgreSQL or desktop SQLite, OpenAPI at `/api-docs`.
- `apps/web` — **SvelteKit on Bun** frontend (`pdmux-web`), Tailwind v4 + shadcn-svelte + typesafe-i18n.
- `apps/desktop` — Electron lifecycle shell that embeds the same API and web builds with local providers.
- `infra/` — provider-aware Docker Compose and example k3s manifests.
- `.podokit/` — PodoKit generation metadata plus application-owned development and
  deployment profiles (see "PodoKit tooling" below).

## Setup & commands

Inspect active infrastructure with `podo provider list`. New-project defaults
are `database=postgres`, `cache=redis`, `object-storage=s3`, `events=redis`, and
`jobs=bullmq`. A simple single-process app can instead use `sqlite`, `memory`
cache/events, `local` files, and `local` jobs. Only the database has a creation
flag (`--database`); apply other choices using
`podo provider set <capability> <provider> --apply` before adding features.
Provider selection does not migrate or delete existing data.

**pdmux selects providers at startup, not at generation.** One build serves the
self-hosted server and the desktop shell: `apps/api/src/runtime/providers.ts`
reads `PDMUX_DESKTOP` and the `PDMUX_*_PROVIDER` variables, and
`apps/api/src/config/providers.ts` hands that selection to the PodoKit modules.
Both the server and the local implementation modules are installed, and each
stays inactive unless its provider is selected. `.podokit/manifest.json` records
the server selection for deployments. Do not run `podo provider set`: it rewrites
`config/providers.ts` to fixed values. A provider module must precede the modules
that consume it in the manifest order and in `app.ts`, because a module resolves
its dependencies while it is configured.

```bash
bun install
cp .env.example .env
bun run --cwd apps/api migrate:all
bun run dev        # api on http://localhost:5002, web on http://localhost:5001
```

For PostgreSQL, start `docker compose -f infra/docker/docker-compose.yml up -d`
before migrating. Add `--profile cache` for Redis; Silo uses the overlay from
`object-storage-s3`. Skip external services entirely for the complete local
combination. `podo dev watch` is a separate container workflow and requires
Docker. SQLite and local files default to `./data/podokit.sqlite` and
`./data/files` relative to the API working directory; migrations and runtime
must use the same database path. Keep local providers at one API process.
Merge added module settings from `.env.example` into an existing `.env`.

- **Ports: web = 5001, api = 5002.** The web app reaches the API only through its
  SvelteKit server proxy (`/api/*`), never with a direct browser `fetch`.
- The proxy (`apps/web/src/lib/server/backend-proxy.ts`) is managed and passes only
  allowlisted headers. List extra request and response header names in the
  app-owned `apps/web/src/lib/server/proxy-headers.ts`
  (`APP_FORWARDED_REQUEST_HEADERS`, `APP_RELAYED_RESPONSE_HEADERS`); never edit the
  managed lists. Cap a route's request body in the app-owned
  `apps/web/src/lib/server/body-limits.ts` (`APP_BODY_LIMITS`, 413
  `PAYLOAD_TOO_LARGE`). `BODY_SIZE_LIMIT` is the ceiling for every web route, so
  uploads larger than it must use a direct API path (`apiPaths`) instead. Give a
  route a longer, shorter, or no response deadline in the app-owned
  `apps/web/src/lib/server/proxy-timeouts.ts` (`APP_PROXY_TIMEOUTS`, `null` for
  none); never edit the managed deadline. Both lists take path prefixes with
  `:name` parameters, such as `/api/hosts/:hostId/file-transfers`, and the most
  specific prefix wins.
- Server-side API calls (`serverApiClient`) give up after `BACKEND_TIMEOUT_MS`
  (2000), and the proxy answers 504 `BACKEND_TIMEOUT` when the API sends no
  response headers within `BACKEND_PROXY_TIMEOUT_MS` (30000). Once the API's
  `GET /health` stops answering too, calls throw `BackendUnavailableError` and the
  proxy answers 503 `BACKEND_UNAVAILABLE` at once until it answers again. Handle
  any non-`ApiError` failure in a load function as a temporary outage. The API
  (`API_IDLE_TIMEOUT`) and the built web server (`CONNECTION_IDLE_TIMEOUT`) close
  a connection that sends nothing for that many seconds (35 each): raise both
  with any longer `BACKEND_PROXY_TIMEOUT_MS` or `APP_PROXY_TIMEOUTS` entry, more
  than 4 above it, or set `0` when a route has no deadline. The proxy refuses to
  load when `CONNECTION_IDLE_TIMEOUT` cannot cover a deadline.
- Read a caller's address in the API with `clientAddressOf(request.headers)` from
  `apps/api/src/core/client-address.ts`, never from `X-Forwarded-For` directly. The
  API resolves it once per request from `TRUSTED_PROXY_HOPS` (1: the web proxy) and
  `TRUSTED_PROXY_HEADER`; Better Auth sessions, audit entries, and rate limits use
  the same address.
- pdmux keeps the managed proxy unchanged. File transfers
  (`/api/hosts/:hostId/file-transfers`) have no proxy deadline in
  `APP_PROXY_TIMEOUTS` and their chunk route a 1 MiB cap in `APP_BODY_LIMITS`,
  because the API's agent deadlines (up to five minutes for a commit) own that
  wait. A route without a deadline needs `CONNECTION_IDLE_TIMEOUT=0` wherever the
  built web server runs (the web image, the desktop shell, the k3s ConfigMap, and
  the deployment profile's `runtimeConfig`); the API instead lifts its idle
  timeout per request on the transfer routes that wait. The origin the caller
  reached travels to the API in `x-pdmux-caller-origin`, which the `/api` and
  `/mcp` routes set (`apps/web/src/lib/server/caller-origin.ts`), since the proxy
  reserves `X-Forwarded-Host`. See `docs/FILE-TRANSFERS.md`.
- `GET /healthz` (`apps/web/src/routes/healthz/+server.ts`) is the web server's own
  health route for the Kubernetes probes, the Compose healthcheck, and the image
  `HEALTHCHECK`. Keep it free of API calls, so an API outage does not take the web
  out of service.
- When the root layout or a server hook fails, such as with 503 while the API is
  down, SvelteKit serves the app-owned `apps/web/src/error.html`. It is plain HTML
  with inline styles: no components, app CSS, scripts, or assets, and only the
  `%sveltekit.status%` and `%sveltekit.error.message%` placeholders.
- Build: `bun run build` · Type-check/lint: `bun run lint` · Unit tests: `bun run test`
- Per workspace: `bun run --cwd apps/api build` / `bun run --cwd apps/web build`.
- Set up the database and apply later migrations, including after adding a module, with
  `bun run --cwd apps/api migrate:all`. It applies the Better Auth schema before the application
  migrations, and on the desktop SQLite provider it creates the schema (module tables plus entity
  synchronization). It runs the source in development and the compiled bundle in a production image
  (`NODE_ENV=production`), from `apps/api` so Bun applies the API's decorator settings.
- `bun run --cwd apps/api migration:run` runs only the PostgreSQL application migrations and never
  creates Better Auth tables; on a new database `IndexSessionCreatedAt` stops and names `migrate:all`.
  `bun run --cwd apps/api migration:revert` reverts the latest application migration.
- PostgreSQL migrations are statically registered in `apps/api/src/database/migrations.ts` and
  embedded in the API bundles. Register every new migration there without renaming or editing
  historical migrations. The build rejects a missing registration; do not restore runtime globs.
- Run `bun run test:migrations` for database or migration-build changes. It builds the API and tests
  fresh install, populated legacy-schema upgrade, rollback, and rerun against disposable PostgreSQL.
  API and worker startup must refuse pending migrations; never bypass this gate to make a rollout pass.
- Run `bun run test:database-recovery` for changes to API startup or database access. It starts the API
  from source against disposable PostgreSQL, then stops, pauses, and restarts the database, and checks
  that the API listens, answers 503 `DATABASE_UNAVAILABLE`, and recovers without a restart.
- Run `bun run test:redis-recovery` for changes to API startup, job scheduling, or Redis access. It
  starts the API and the worker from source against disposable PostgreSQL and Redis, starts the API
  with Redis stopped, then replaces Redis with an empty one, and checks that the API listens, answers
  503 `JOBS_UNAVAILABLE` at once, schedules the maintenance jobs again, and that the worker runs jobs.
- CI also builds and tests final API images on native AMD64 and ARM64 runners without publishing them.
  Both migration-image jobs must pass before merging migration or packaging changes.
- e2e (Playwright, ships in `tests/`): `bun run test:e2e`.
- Playwright officially runs on Node, so `bunx playwright` respects its Node
  shebang. Node LTS is a test-tool dependency only; product runtimes and builds use Bun.

**Always** verify a change by building the affected workspace (and `svelte-check`
for web) before considering it done. UI changes need a Playwright test; API
changes need an e2e/unit test.

**Run the tests that cover the change, not the whole suite.** The full e2e sweep is
~5 minutes serial and it is the wrong loop for a one-file fix; a change is verified by
the specs that assert its behaviour plus the unit suite of the package it lives in.
Reserve the full sweep for a release, a periodic check, or a change with global reach
(the shell's stylesheet, a `@pdmux/core` reducer, the protocol, an auth or layout
default). Picking the related specs is part of the work — say which ones and why.

```bash
# unit, one package
bun run --cwd packages/core test   # or packages/ui, apps/api, apps/web
# e2e, one spec file or one TC
cd tests && bunx playwright test --project=ui --workers=1 ui/pdmux-dashboard.ui.spec.ts
cd tests && bunx playwright test --project=ui-mobile --workers=1 -g 'TC-PDTERM-124'
```

Which specs cover which change is decided by where the change lands: a component's own
`test/` for a component, `apps/api`'s jest suite for an endpoint, `agent`'s `go test` for
the agent, and one Playwright file for a screen. The `[TC-…]` tag in a test title is what
ties it back to the requirement it was written for.

## Code style

### TypeScript (both apps)
- `strict` mode. **No `any`** — use `unknown` + narrowing. **No `@ts-ignore`/`@ts-expect-error`** and no `eslint-disable`.
- Explicit function return types. Validate HTTP inputs with Elysia `t` schemas.
- Keep `noUnusedLocals`, `noUnusedParameters`, `noImplicitReturns`, `noUncheckedIndexedAccess`.

### Svelte 5 (web)
- **Runes only**: `$state()`, `$derived()`, `$effect()`, `$props()`. **Never** use `$:` (deprecated).
- Reactive stores go in `.svelte.ts` files; don't destructure a getter-exported rune (it loses reactivity) — wrap in `$derived`.

### UI — Tailwind + shadcn-svelte (web)
- Prefer **shadcn-svelte components** over raw HTML (`<button>`, `<input>`, `<select>`, …).
- **Do not edit `src/lib/components/ui/**`** (the shadcn primitives). Customize in a separate wrapper.
- Tailwind v4 (CSS-first, no `tailwind.config`). Use semantic classes: `bg-background`, `text-foreground`, `border-border`. Dark mode via `mode-watcher`. Responsive (`sm:`/`md:`/`lg:`).

### i18n & errors
- **Every user-facing string goes through i18n** (`src/lib/i18n/messages.ts`) — no hardcoded text. Add keys to **all** locales at once.
- The backend returns a stable **error envelope**: `{ success: false, error: { code, message, statusCode, path, timestamp, details? } }`. Throw `AppException("SOME_CODE", ...)` on the backend; **branch on `error.code`, not the message,** on the frontend.
- Logging is structured; no emojis/icons. Start messages with an action verb.

## PodoKit tooling & file ownership

This project is managed by the `podo` CLI. Files have an ownership tier recorded
in `.podokit/files.lock` — respect it:

- **owned** (your code: `apps/web/src/routes/**`, your components/services, `apps/api/src/app.extensions.ts`, and this `AGENTS.md`) — edit freely. Add application-owned services or module descriptors through `app.extensions.ts` instead of changing toolkit registrations. Set Bun server options (`maxRequestBodySize`, `idleTimeout`) with its `apiServerOptions` export rather than editing `main.ts`; `API_MAX_REQUEST_BODY_SIZE` and `API_IDLE_TIMEOUT` apply when the export leaves them out.
- **assembled** (e.g. `apps/api/src/app.ts`, `auth.ts`) — contain `// podokit:begin:… / …:end` fenced regions that the toolkit recomputes. Edit outside the fences only; **never hand-edit inside the fences**.
- **managed** (bootstrap/config like `main.ts`) — the toolkit may update these; avoid gratuitous edits.

Useful commands:

- `podo dev watch|up|ps|logs|exec|down` — run container development through the
  shared loopback gateway. `.podokit/dev.json` owns the local hostname and exact
  API WebSocket path allowlist.
  `podo dev up` rebuilds the images from the current source so a recreated
  container never runs code older than the files Compose Watch synced.
  `podo dev down` also stops this project's running `podo dev watch`; do not
  kill Compose processes by hand.
  The containers read the untracked `.env.docker`; `podo dev` creates it from the
  committed `.env.docker.example` with generated secrets when it is missing. Never
  commit `.env.docker` or put secrets in the example.
- `podo add <module>` — add a feature (auth, admin-dashboard, redis, bullmq, …). It wires itself into the app; run `podo add` with no argument to list modules.
- `podo remove <module>` — un-apply a module (inverse of add; refuses if another module needs it, keeps files you edited).
- `podo provider list` / `podo provider set <capability> <provider> [--apply]` — inspect or switch database, cache, object storage, events, and jobs. Set is dry-run by default and never migrates or deletes provider data. Local providers require one API process.
- `podo status` / `podo diff` — see your local edits vs. what PodoKit generated.
- `podo update` — pull in template/module improvements (3-way merges your edits; never touches owned files).
- `podo deploy` — plan, apply, verify, or roll back an immutable release on Kubernetes or one Docker host. Production API WebSocket paths belong in the deployment profile's exact `exposure.webSocketPaths` allowlist, and API routes that take bodies above the web server's `BODY_SIZE_LIMIT` (file uploads) in `exposure.apiPaths` (and `.podokit/dev.json` `apiPaths` for `podo dev`; `podo add` and `podo deploy init` fill in the paths modules declare), which reach the API without the web proxy, so the API must check their size, session, and `Origin` itself; Compose trusts forwarding headers only from `exposure.trustedProxyCidrs`. Tag `vX.Y.Z` to build and push the images (`.github/workflows/release.yml`; check its runner — GitHub-hosted minutes are free for public repositories only). Use `.agents/skills/podokit-deploy`.
- `podo deploy sync` — copy local build output into a running Compose deployment and restart it, for iterating without a release. Not a release: no image is published and the next `apply` discards it. Use `.agents/skills/podokit-deploy-fast`.

**⚠ `/account` moved into the product shell.** It lives at `apps/web/src/routes/(shell)/account/` (page + loader,
the loader ejected with `podo eject` and moved) so the host sidebar stays put, exactly like `/hosts`. `podo update`
still offers to **add** `apps/web/src/routes/account/+page.server.ts` — do not take it: SvelteKit would then have two
routes matching `/account` and the build fails. Either drop that add or move its content into the group's loader.
The screen itself is PodoKit's `account-page.svelte` (managed, reused whole), so updates to it arrive normally.

≤50-char subject, no trailing period, no emojis. One logical change per commit.

### mailer
- Send email with `import { sendMail, actionEmail } from "../mail/mailer"` (path relative to your file). `sendMail({ to, subject, text, html? })`.
- SMTP comes from the admin Settings page (when auth is installed) or `SMTP_*` env; with neither, messages are logged to the console (dev links are grabbable from logs).
- To use a provider SDK instead of SMTP, call `setMailTransport(...)` from `apps/api/src/app.extensions.ts`.

### auth (Better Auth + Elysia)
- The API is secure by default: every application route needs a session except health, OpenAPI, `/api/auth/*`, and routes explicitly registered in `ACCESS_POLICY`.
- Register a public route during module configuration with `services.resolve(ACCESS_POLICY).register("GET", "/path", "public")`; use `AUTH` and `AuthService.requireSession()` or `requireAdmin()` when a handler needs the current user.
- Configure OAuth providers, SMTP, sign-up approval, automatic logout, and server toggles on the admin Settings page. Only `BETTER_AUTH_SECRET` and `BETTER_AUTH_URL` are required environment variables.
- Use `bun run --cwd apps/api auth:configure -- ...` and `.claude/skills/podokit-configure-auth` to apply OAuth/SMTP credentials without committing secrets. The sign-up approval gate is provider-independent; do not add provider-specific approval checks.
- Run `bun run --cwd apps/api migrate:all` in development and production so Better Auth and application migrations use the versions installed by the app.
- Back up existing databases before upgrading authentication. Migrations check duplicate `(providerId, accountId)` identities and clean up obsolete issuer constraints; resolve reported collisions manually rather than guessing account ownership.

### admin-dashboard
- Admin console lives at `/admin/*` (users, sessions, organizations, audit, settings, account). Set `ADMIN_EMAILS`, then create or verify the initial account with `bun run --cwd apps/api admin:bootstrap`; never commit or persist `ADMIN_BOOTSTRAP_PASSWORD`. When sign-up approval is enabled, self-registered users stay pending until an administrator approves them on `/admin/users`; administrator-created users bypass the queue.
- Custom protected server layouts must call `requireBackendAvailable(locals)` from `$lib/server/guards` before redirecting anonymous users. This preserves sessions and returns 503 when authentication or maintenance policy cannot be checked.
- Every page except the sign-in flow, `/`, and module pages requires a session, and fails closed with 503 when the API or site settings are unavailable. List the application's public pages (such as `/install.sh`) in `APP_PUBLIC_PATHS` in the app-owned `apps/web/src/lib/server/public-paths.ts`; a prefix covers its subpaths. Do not edit the `PUBLIC_PATHS` list in the managed `guards.ts`.
- `hooks.server.ts` loads the site settings and the session for pages, page data, form actions, remote functions, and the 404 page. When a `+server.ts` endpoint serves files or feeds that need neither, list its prefix in `APP_ASSET_PATHS` in the app-owned `apps/web/src/lib/server/asset-paths.ts` to skip both API calls; such endpoints see an anonymous `locals.user`, and page requests under the prefix still get the full context.
- **Every list/table MUST use the shared `$lib/components/data-table.svelte` (`DataTable`)** — it gives sortable headers + a footer pagination. Add search/filters with `$lib/components/table-toolbar.svelte`. Never assemble `Table.Root`/`Table.Header`/`Table.Body` by hand.
